     Growtick Website v1 — Implementation Plan

     Context

     Growtick_Website_PRD.pdf (v1.0, 4 Nov 2026) asks for a mobile-first website
     to replace Growtick's PDF brochure. It needs a very light 3-section home
     page (hero, carousel of 19 services, contact), inner pages, lead capture
     (form, call, WhatsApp), and a small admin panel with roles and 2FA. Speed
     targets are strict: PageSpeed 90+ on every page and 95+ on the home page,
     with the home page under 500 KB and under 50 KB of JS. The project folder
     holds only the PDF, so this is a new build.

     Build steps

     1. Scaffold and design system

     - Set up Astro + TypeScript. Self-host Space Grotesk 500/700 as woff2 via
       @fontsource, subset to Latin, and preload it.
     - Put light/dark CSS tokens on :root. A small inline script runs before
       paint so the page doesn't flash: it reads localStorage first, then
       prefers-color-scheme.
     - Mobile-first layout: cards stack below 640px, tap targets are at least
       44px, and focus outlines are visible.
     - One inline SVG icon sprite: graduation cap, bulb, rocket, megaphone,
       printer, gift, handshake, scales, plus UI icons.

     2. Content model

     - Write content/services/*.md for all 19 services. Frontmatter holds
       number, slug, pillar (one of the 5), title, 8-word hook, icon, SEO title
       and description, and related FAQ ids. The body holds the full bullets.
       Copy comes from PRD pages 6–7.
     - Soften brochure claims as the PRD's copy note asks: "Top Search Rank"
       becomes "improved local visibility".
     - Seed the FAQ list with the 10 starter questions. Answers are placeholders
       marked TODO.
     - Write 3 sample testimonials with sample: true. They are filtered out of
       production builds.

     3. Home page (3 sections only)

     - Hero: an animated SVG logo (CSS keyframes, plays once, under 1.5s, fixed
       size so the layout doesn't shift, respects reduced motion), the GROWTICK
       name, the positioning line, Call Now and WhatsApp buttons, and one SVG
       illustration under 30 KB.
     - Carousel: a CSS track holding the 19 cards twice for a seamless loop,
       driven by under 10 KB of vanilla TS. It auto-scrolls slowly and pauses on
       hover, focus or touch. Native scroll-snap handles swipe. Arrow buttons
       and keyboard work. With reduced motion it becomes a plain horizontal
       scroll row. About 1.2 cards are visible on mobile and 3–4 on desktop.
       Each card has "Know more" (links to /services/slug) and "Enquire" (goes
       to #contact?service=slug and pre-selects the service). A "View all
       services" link sits below.
     - Contact: a short form (name, phone, service) plus Call, WhatsApp and
       Instagram links. The floating WhatsApp button hides while this section is
       in view, using IntersectionObserver.
     - Budget is enforced in CI: under 500 KB, under 50 KB JS, under 15
       requests.

     4. Inner pages

     - /services: all 19 grouped into 5 pillars. Filter chips use CSS :has()
       with a tiny JS fallback.
     - /services/[slug]: one template for all 19 pages. Each has full bullets,
       related FAQs, Enquire (links to /contact?service=slug), Share to
       WhatsApp, and Service JSON-LD.
     - /academy (services 01–02, with duration, batches and "fees on request"),
       /testimonials (same carousel component plus a grid), /faq (accordion with
       FAQPage JSON-LD), /about, /contact (full form, map embed loaded only on
       click or placeholder until an address exists, hours, all channels),
       /privacy (DPDP notice), and a custom 404 page.
     - Header has logo, menu (Services dropdown of the 5 pillars), dark-mode
       toggle and Call. On mobile the menu is a full-screen hamburger. Footer is
       one line: tagline, Instagram, Share to WhatsApp, Privacy, ©.

     5. Supabase backend

     - Tables: leads, services, faqs, testimonials, profiles(role: 
       owner|editor|viewer), activity_log, rate_limits.
     - RLS rules:
       - The public role can't read anything; leads are inserted only by the
         server function using the service key.
       - Viewers can read leads.
       - Editors can write content.
       - Owners can do everything, including managing users.
       - Every policy requires auth.jwt()->>'aal' = 'aal2', so 2FA is mandatory.
     - Triggers on every content and lead table write rows to activity_log (who,
       what, before/after).
     - Supabase daily backups (30 days on the Pro plan; the README notes the
       plan requirement) plus the weekly Markdown export.

     6. Lead endpoint (/api/lead, Cloudflare Function)

     - Validates with zod: name required; phone required and must be a 10-digit
       Indian mobile (^[6-9]\d{9}$, +91 prefix stripped); email optional;
       service must be one of the 19 or "Other"; message up to 500 characters;
       DPDP consent required.
     - Spam and abuse protection: a honeypot field, server-side Turnstile check,
       and a limit of 5 submissions per IP per hour (counted in the rate_limits
       table with a hashed IP).
     - Saves the lead, then sends a Resend email alert. If the email fails, the
       lead is still saved and the error is logged.
     - If the save fails, the client shows an inline error with Call and
       WhatsApp fallbacks and a Retry button. Field errors appear inline in
       plain language, and the form also works without JS (progressive
       enhancement).

     7. Admin panel (/[ADMIN_PATH])

     - Built as a Preact island with supabase-js. It loads only on admin routes,
       so public pages carry none of its JS.
     - Login is email and password, followed by TOTP enrolment and verification
       (Supabase MFA). Supabase rate-limits login attempts, and the UI adds a
       lockout message.
     - Leads: filter by service and date, change status (New, Contacted,
       Converted, Closed), export CSV.
     - Content: add, edit and delete testimonials and FAQs (order, published
       flag), and edit service text. A Publish button calls /api/publish, which
       triggers the deploy hook.
     - Users (Owner only): invite, change role, remove.
     - Activity log viewer.

     8. SEO, security, ops

     - Every page gets a unique title and meta description (local keyword + city
       from site.ts), one H1, a canonical URL and OG tags. JSON-LD covers
       LocalBusiness/ProfessionalService, Organization (with Instagram) and
       FAQPage.
     - The sitemap is generated automatically.
     - public/_headers sets HSTS, CSP (self + Turnstile + CF analytics),
       X-Frame-Options DENY, Referrer-Policy, and Permissions-Policy, plus long
       cache lifetimes on hashed assets.
     - Outbound links use target=_blank rel="noopener", and CI runs a
       broken-link check.
     - Server errors are logged and emailed to the owner through Resend. The
       README covers uptime monitoring (e.g. UptimeRobot free tier) and turning
       on the Cloudflare WAF.

     9. Backup and repo

     - scripts/export-to-markdown.ts pulls services, FAQs and testimonials from
       Supabase into content/. A weekly GitHub Action runs it and commits any
       changes.
     - scripts/seed-from-markdown.ts does the reverse, to restore or set up a
       fresh database.
     - I'll run git init locally. You create the GitHub repo and set up main
       branch protection (steps in the README).

     Not in v1 (per PRD)

     Payments or enrolment, student portal, blog, Hindi/Kannada versions, client
     portal, WhatsApp/SMS alerts.

     Verification

     1. npm run dev with no Supabase env: the site renders from Markdown, so you
        can click through every page, both themes and the mobile menu.
     2. npm run build && npm run check:budgets: checks home page size, JS size
        and request count, and that there are 19 service pages.
     3. Lighthouse CI (mobile) on the built site: 95+ on home and 90+ on inner
        pages, across all four scores.
     4. Local Supabase (supabase start): apply migrations, seed, submit the form
        (valid, invalid, honeypot, 6th submission in an hour gets blocked),
        confirm the lead row exists and the email goes out (Resend test key),
        and check the fallback UI when the database is stopped.
     5. Admin: enrol TOTP, check each role's access (Viewer can't edit, Editor
        can't manage users), lead status changes, CSV export, activity log
        entries, and that Publish calls the hook (mocked locally).
     6. Manual checks: carousel loops, swipes, pauses, and works by keyboard and
        with reduced motion; dark mode on every page; WhatsApp chat and share
        links; keyboard-only navigation; axe accessibility check.
     7. Turn the PRD pre-launch checklist into LAUNCH_CHECKLIST.md, marking the
        items that need real accounts or content (2 owner admins, domain lock,
        real testimonials, licensed illustrations).
